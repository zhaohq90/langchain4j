# Tools

在 LangChain4j 中，**Tools** 用来让模型具备“调用外部能力”的可能性。很多人把它理解为函数调用，这个理解是正确的，但如果从系统设计角度看，Tools 的意义更大：它把原本只能“生成文本”的模型，扩展成了一个可以根据上下文选择并触发业务动作的执行型组件。

一个没有 Tools 的模型，通常只能根据已有知识与上下文生成回答。一个具备 Tools 的模型，则可以在需要时调用你提供的函数，例如查询订单、检索数据库、访问业务服务、执行搜索、触发工作流等。

## Tools 的作用

Tools 的本质，是在模型和应用系统之间建立一个受控接口。模型不直接访问你的数据库或内部系统，而是通过你声明的工具方法进行调用。这种方式既有利于能力扩展，也有利于安全控制。

| 作用 | 说明 |
|---|---|
| 能力扩展 | 让模型超越训练知识边界，调用实时或私有系统能力 |
| 业务执行 | 让模型能够触发业务函数，例如查订单、建工单、执行检索 |
| 决策驱动 | 由模型根据上下文决定是否调用工具 |
| 安全隔离 | 模型只能通过你暴露的接口访问受控能力 |

## 为什么 Tools 是进阶学习的分水岭

在学习 LangChain4j 的过程中，Tools 是一个非常重要的转折点。因为从这里开始，系统不再只是“问答机器人”，而是逐步演变成“会行动的助手”。

例如，一个简单聊天系统只能告诉用户“你可以联系售后取消订单”；而一个具备 Tools 的系统，则可能真正调用取消订单接口，查询订单状态并返回执行结果。

## 与 AI Services 的关系

Tools 通常与 `AI Services` 结合使用。也就是说，你可以在一个接口式的 AI 助手中注册一个或多个工具，让模型在对话过程中根据工具描述自行决定是否触发对应方法。

这种模式特别适合构建任务型 AI 助手，因为业务逻辑依旧由 Java 方法承载，而模型只负责判断“什么时候需要调用哪个工具”。

## 设计 Tools 时应关注什么

从工程实践上看，设计一个好的 Tool，不只是把某个方法暴露给模型。更重要的是，你要清晰定义该工具的职责边界、输入参数、返回结果与描述信息。工具描述越准确，模型越容易在正确的场景下做出正确调用。

因此，在 Tools 学习阶段，建议重点关注三件事：第一，如何清晰描述工具用途；第二，如何设计稳定且易理解的输入输出；第三，如何对工具执行做日志、监控与权限控制。

## Tools 在后续主题中的地位

Tools 不只是单独存在的一个能力。它实际上是后续多个高级主题的基础。

| 后续主题 | 与 Tools 的关系 |
|---|---|
| RAG | 检索本身也可以被工具化 |
| Agents | Agent 往往依赖工具完成实际动作 |
| MCP | MCP 可以把外部能力通过统一协议接入为工具 |
| Skills | Skills 常被理解为更高层、更可复用的能力封装 |
| 多 Agent | 多个代理之间的分工，常常围绕不同工具能力展开 |

## 学习建议

如果你已经完成了基础聊天与 AI Services，Tools 通常是下一步最值得学习的内容。因为它能让你最快看到“模型真正参与业务执行”的价值。等你理解 Tools 之后，再学习 RAG、Agents、MCP 与多 Agent，会更容易理解这些高级能力为什么成立。
