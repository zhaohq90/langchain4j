# Agents

在 LangChain4j 的能力体系中，**Agents** 代表从“模型回答问题”走向“模型理解任务、拆解步骤、调用能力并推进执行”的关键阶段。它不是单一功能点，而是一种更高层的系统设计方式。

如果说基础聊天解决的是“模型怎么回答”，RAG 解决的是“模型如何基于知识回答”，那么 Agents 进一步解决的是“模型如何围绕目标组织行动”。

## Agent 的核心思想

一个 Agent 的核心，不在于它是不是用了某个特定类，而在于它是否具备以下能力：理解目标、判断下一步该做什么、在必要时调用工具或其他能力、根据结果继续推进流程，并在多步之后返回较完整的任务结果。

这意味着 Agent 本质上更像一个“任务推进器”，而不是单轮对话接口。

| 能力维度 | 说明 |
|---|---|
| 目标理解 | 理解用户任务而不是只处理一句话 |
| 步骤规划 | 能决定先做什么、后做什么 |
| 能力调用 | 在需要时使用工具、检索、外部系统或其他代理 |
| 状态推进 | 根据中间结果继续行动，而不是只回复一次 |
| 结果整合 | 将多步执行结果整理为最终输出 |

## 为什么 Agent 很重要

很多真实业务并不是一次回答就能解决的。例如“帮我调研一家公司、总结风险并给出行动建议”“帮我检查知识库回答是否缺证据”“帮我完成一个需要搜索、提取、判断和写作的任务”。这些任务都更像流程，而不是单个问题。

Agent 正是在这种背景下出现的。它让大模型从“语言生成器”向“面向任务的执行协调者”演进。

## LangChain4j 中的 Agent 学习重点

在 LangChain4j 中学习 Agents，建议重点理解以下几个层面。第一，Agent 与 Tools 的关系，因为绝大多数可执行 Agent 都需要工具支持。第二，Agent 与 RAG 的关系，因为知识检索常常是 Agent 决策的一部分。第三，Agent 与 Skills、MCP、A2A 的关系，因为这些能力会决定 Agent 如何连接更多外部能力或其他代理。

## 多 Agent 与 Subagent

当单个 Agent 难以覆盖全部职责时，系统就会进入 **多 Agent** 模式。此时不同 Agent 可以承担不同角色，例如一个负责规划，一个负责检索，一个负责执行，一个负责审校。

从工程角度看，**Subagent** 可以理解为被上层 Agent 调用或编排的下级代理。它通常承担某个更专门、更聚焦的职责，而不是直接面向最终用户。这样的分层有助于降低单一代理的职责复杂度，也更有利于复用与治理。

| 角色类型 | 典型职责 |
|---|---|
| 主 Agent | 接收总体目标、分派任务、汇总结果 |
| 检索 Agent | 专注知识查询与证据召回 |
| 工具 Agent | 专注调用外部系统或业务工具 |
| 审校 Agent | 负责校验答案、检查结构与风险 |
| Subagent | 作为子能力单元，由上层 Agent 在流程中调用 |

## 为什么要学习 Subagent

你提到的 subagent，实际上是从“一个大而全的代理”走向“职责分解与分层协作”的关键概念。对于复杂业务系统来说，这种设计非常重要。因为它可以把搜索、推理、执行、审校等职责拆成更独立的单元，从而提升系统稳定性、可维护性与可观测性。

## 学习建议

如果你已经完成基础聊天、AI Services、Tools 和 RAG，那么进入 Agents 阶段时，建议不要一开始就追求过于复杂的多 Agent 架构。更好的方式是先理解单 Agent 如何结合工具与检索完成任务，再逐步演进到主 Agent + 子 Agent 的层次结构，最后再考虑多 Agent 协作、A2A、MCP 与更复杂的模式化工作流。
