# RAG

**RAG（Retrieval-Augmented Generation，检索增强生成）** 是 LangChain4j 中最重要的进阶能力之一。它的目标不是让模型凭空回答，而是让模型在回答前先获取与你的业务知识相关的外部内容，再基于这些内容生成答案。

对于企业应用而言，RAG 往往是从“通用聊天助手”走向“企业知识助手”的关键一步。因为通用模型虽然拥有广泛的公共知识，但并不了解你的内部文档、产品资料、操作手册、FAQ、合同模板、规范制度或实时业务数据。

## RAG 的基本链路

在 LangChain4j 的语境里，RAG 并不只是简单地“做一次向量检索”。更准确地说，它是一条包含多个环节的数据与推理链路。从整体上看，它通常分为两个阶段：**数据导入阶段**与**查询检索增强阶段**。

| 阶段 | 主要内容 |
|---|---|
| 数据导入 | 加载文档、解析内容、切分文本、生成 embedding、写入向量存储 |
| 查询增强 | 对用户问题进行处理、检索相关片段、必要时重排，再把结果交给模型生成答案 |

因此，学习 RAG 时不能只盯着“向量库怎么查”，还要理解数据从哪里来、如何被处理、检索结果如何进入回答过程，以及每一步如何影响最终质量。

## LangChain4j 中的 RAG 组成

LangChain4j 针对 RAG 提供了比较完整的支持能力。你通常会接触到以下几类组件：文档加载器、文档解析器、文本切分器、嵌入模型、Embedding Store、内容检索器以及 Retrieval Augmentor 等。

这些组件共同构成了一条从原始知识到增强回答的完整路径。

## 为什么 RAG 很重要

如果你要构建的是一个真正可用于企业知识问答、内部文档助手、法规问答、产品支持助手或搜索增强型 Copilot，那么 RAG 通常不是可选项，而是核心能力。因为它解决的是模型最根本的问题之一：**缺少你的私有知识**。

没有 RAG，模型很可能只能根据参数记忆和用户当前输入进行推测；有了 RAG，模型才能在回答时参考真实资料，从而提高准确性、可解释性与业务适配度。

## RAG 的学习重点

学习 LangChain4j 的 RAG 时，建议重点关注四个层面。第一，如何导入和处理知识源；第二，如何选择嵌入模型与向量存储；第三，如何设计检索链路；第四，如何把检索结果与模型生成过程结合起来。

真正的难点通常不是“代码能跑通”，而是“效果是否好”。而效果问题往往来自切分策略、知识质量、查询改写、检索召回、重排策略以及提示词注入方式等多个环节。

## 与 AI Services、Tools、Agents 的关系

在 LangChain4j 中，RAG 并不是孤立存在的。它经常会与 AI Services 配合，形成一个带知识增强的问答助手；也可以以 Tool 的形式暴露给模型，让模型在需要时自行决定是否触发检索；在更复杂的 Agent 系统里，RAG 还可能成为某个子代理的专门能力。

因此，从学习路径上看，RAG 通常位于“基础聊天之后、复杂 Agent 之前”的关键阶段。它让系统先学会“基于知识回答”，再进一步过渡到“基于知识与工具执行任务”。
